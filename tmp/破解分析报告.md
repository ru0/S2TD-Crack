## 3. 打包与保护层

### 3.1 PyInstaller

解包目录含典型结构：`pyiboot01_bootstrap`、`PYZ-00.pyz`、`python310.dll`、`base_library.zip`。入口不是普通 `__main__`，而是混淆后的 `Session.2.TData_CN_MT`。

### 3.2 PyArmor 特征

入口/业务 pyc 头部可见：

```text
PYARMOR \x00\x00 \x03\n ...
```

- `\x03\n` = Python **3.10**
- 同目录存在 `_pytransform.dll`（约 1.1MB）
- DLL 字符串含 `PYARMOR`、`Check license failed`、`pyarmor-vax` **不存在**、`get_error_msg has been removed from PyArmor v5.7.3` 等 → **旧版 core（非 PyArmor 8+ VAX runtime）**
- 源路径残留：`dist\obf\Session.2.TData_CN_MT.py`

### 3.3 与 pyarmor-1shot 的匹配性

`pyarmor-1shot` 的 `RuntimeInfo` 依赖在 runtime 中定位 `pyarmor-vax` 并解析 AES key。对本包：

```text
RuntimeInfo(_pytransform.dll) -> ValueError: subsection not found
pyarmor-vax offset = -1
```

因此：**不能指望当前 1shot 工具直接脱壳**；需改用针对 `_pytransform` / PyArmor5–7 的方案，或改为 **运行时 dump**（Frida/内存取码）。

## 4. 授权与网络协议

### 4.1 本地 License

`S2TD_LicenseKey.txt`：

```text
S2TD-KTDP3JT-3TKJ7XN-YHL0LW4
```

格式：`S2TD-` + 三段字符。真正有效性由服务端裁决；本地可能仅做格式/缓存校验（逻辑在装甲模块内）。

### 4.2 API 与 mTLS

`get.txt` 请求要点：

| 字段 | 值 |
|---|---|
| 方法/路径 | `GET /api/v2/get-csrf-token`（注意：带 JSON body，非常规纯 GET） |
| Host | `lic.megacave.com` |
| Header | `Cf-Client-Cert-Der-Base64: <PEM证书再Base64>` |
| Body | `{"data":"...","key":"..."}` |

`demo/` 中证书三份同源：

- Subject：`CN=megacave.com, O=MegaCave, email=abuse@megacave.com`
- Issuer：Cloudflare Managed CA
- Serial：`52BFFC40F80002868FD599F03C66F84A98737EBB`
- 公钥：**RSA-4096**
- `tmpvzd2agdz.pem` 与证书匹配（已验证）
- 有效期：2024-07-14 → 2039-07-11

这是 **Cloudflare 双向 TLS 客户端证书**，用于证明调用方身份；与 Body 内 RSA-2048 业务加密是两套密钥。

`readme.txt` / `simple_client_test.py` 已给出复现路径：

```bash
curl -v --cert cert.crt --key tmpvzd2agdz.pem https://lic.megacave.com/api/v2/get-csrf-token
```

或：`openssl pkcs12 -export ...` 导入系统后由浏览器/工具使用。

### 4.3 Body 加密结构（线上已验证）

对 `get.txt` / `latest_body.json` 解析与实机解密：

1. `data`：Base64 → ASCII Fernet token（前缀 `gAAAAA...`）
2. `key`：urlsafe/标准 Base64 → **256 字节** → RSA-2048 密文

```text
明文 JSON
    → Fernet(AES-128-CBC + HMAC)  → token（data）
    → RSA_ENCRYPT(fernet_key, 对方公钥, OAEP-SHA256) → key
    → JSON {data: b64(token), key: b64(rsa_ct)}
```

**方向与密钥：**

| 方向 | `key` 用谁的公钥加密 | 谁能解密 | 当前材料 |
|---|---|---|---|
| 客户端 → 服务端（请求，如 `get.txt`） | **服务端公钥** | 仅服务端 | 客户端私钥解不开（正常） |
| 服务端 → 客户端（响应） | **客户端 Body 公钥** | 客户端 2048 私钥 | **已掌握，可解密** |

**密钥归属（2026-08-01）：**

| 密钥 | 位数 | 作用 | 状态 |
|---|---|---|---|
| mTLS 客户端证/钥 | 4096 | Cloudflare 双向 TLS | 已掌握（见 §5.1） |
| Body 客户端私钥 | 2048 | 解密服务端响应 `key` | **已掌握** `tmp/captured/keys_clean/body_rsa2048_private.pem` |
| Body 服务端公钥 | 2048 | 加密请求 `key` | **已确认** `keys_clean/server_pub.pem`（fp=`67e373694bf5a073`，线上探测） |
| Fernet session key | urlsafe-44B | 保护业务明文 | 每条消息随机；由 RSA 解出 |

**关于 `demo/rsa_test.py`：**  
演示「RSA-2048 + Fernet」形态，但硬编码密钥 **≠** 线上 body 密钥，padding 为 **PKCS1v15**，与线上响应的 **OAEP-SHA256** 不一致。以扫钥 + `tmp/verify_response_decrypt.py` 为准。

解包目录中 **找不到** 明文 `lic.megacave.com` / `get-csrf-token` / `Cf-Client-Cert` → 藏在业务装甲逻辑里。

### 4.4 启动联网真实明文（v2.2，2026-08-01 已抓到）

程序打开后会自动走授权/更新检查（无需点击联网按钮）。在 **v2.2 CN_MT（PyInstaller）** 上用 Frida spawn + `Fernet.encrypt` monkeypatch，于加密前截获明文。

#### 调用顺序

| # | 方法 | URL | 加密前明文 | 响应明文（客户端私钥可解） |
|---|---|---|---|---|
| 1 | `GET` | `/api/v2/get-csrf-token` | 见下「统一请求明文」 | `{"csrf_token":"..."}` |
| 2 | `POST` | `/api/v2/get-token` | 同上 | `csrf_token` + `access_token`（JWT，`sub=S2TD`） |
| 3 | `POST` | `/api/v2/read-broadcast` | 同上 | 广播 dict（含停更文案） |

样例日志：`tmp/captured/http_capture/requests_v22_20260801_151626.jsonl`。

#### 统一请求明文（三次 API 内容相同）

```json
{
  "token": [
    "S2TD",
    "pbkdf2:sha512:600000$PVOZuzJUaMDf4FN7$6815da8bf46d26b5a2aaa157ef2c979df5ea4790e91e2bdc41b60ca9588132f3d602c18cd7e6fb33fea4e7d8603faa90d962e1cde0b6e18a0dc8a36c00be4271"
  ],
  "product": "S2TD"
}
```

字段说明：

| 字段 | 含义 |
|---|---|
| `product` | 产品标识，固定 `S2TD` |
| `token[0]` | 产品名（与 `product` 呼应） |
| `token[1]` | Werkzeug 风格口令哈希：`pbkdf2:sha512:600000$<salt>$<digest>`；由本地 License（如 `S2TD-KTDP3JT-...`）派生，**不是**明文授权码，也**不是**版本号 |

这与此前 `probe_server_pub_match.py` 模拟发送时服务端依次报错 `"'token'"` → `"'product'"` 完全吻合：业务层只认这两个键。

#### 关于「版本号在不在请求里」

已核对（同一次完整抓包）：

1. **Fernet 加密前明文**：仅有 `token` / `product`，无 `version` / `ver` / `app_version` 等键。  
2. **HTTP 头**（`150502` 完整 headers 日志）：`User-Agent`、`Cf-Client-Cert-Der-Base64`、`X-CSRF-TOKEN`、`Cookie`、`Authorization` 等，**无版本头**。  
3. **JWT**（`access_token`）：`sub=S2TD`，无版本 claim。  
4. **mTLS 证书 Subject**：`CN=megacave.com, O=MegaCave, ...`，无版本扩展。  

停更判定来自 **响应** `read-broadcast`，例如：

```text
product=S2TD
lic_key=
message=This version of the product is no longer supported.
        Please download latest version from our GitHub.
maintenance_state=True
admin_id / bot_token / trial_report / state_report / spare_* / add_info=...
```

即：服务端对产品下发维护/停更广播；客户端请求体**不携带**可读的 `2.2` 版本字段。文件名 `S2TD_Converter_v.2.2_CN_MT.exe` / 入口 `Session.2.TData_CN_MT` 仅为本地构建标识。

#### 主要请求头（业务相关）

| 头 | 作用 |
|---|---|
| `Cf-Client-Cert-Der-Base64` | PEM 客户端证再 Base64（Cloudflare mTLS） |
| `Content-Type: application/json` | 即使 GET 也带 JSON body |
| `X-CSRF-TOKEN` / `Cookie` | 自 `get-csrf-token` 起建立 session |
| `Authorization: Bearer <JWT>` | `get-token` 之后访问 `read-broadcast` |

`User-Agent` 在 CSRF 步为 Chrome 伪装串，后续步可能变为 `python-requests/2.32.3`（同一进程内不同调用路径）。

## 5. 证书与解密密钥获取技术要点

本章汇总两套材料的获取方法：

| 材料 | 章节 | 方法 |
|---|---|---|
| mTLS 客户端证 + 4096 私钥 | §5.1 | Frida Hook OpenSSL（v2.2 路径；v2.5 亦可内存复扫） |
| Body RSA-2048 私钥 | §5.1b | 无注入 `ReadProcessMemory` 扫 PEM（v2.5 推荐） |

### 5.1 客户端证书（mTLS）是怎么抓到的（技术要点）

客户端证书**不是**从磁盘静态文件直接抄出来的，而是通过 **Frida 动态 Hook OpenSSL**，在程序加载证书到 SSL 上下文的瞬间导出。

#### 抓取流水线

```text
realtime_process_monitor.py          dll_detection_hook.js
        |                                      |
        | 1. 启动/附加 S2TD 进程                 |
        | 2. 轮询是否已加载 libssl-1_1.dll      |
        | 3. frida.attach(pid) + create_script  |
        +-------------------------------------->|
                                               |
                          4. Hook LoadLibrary* 等待 libssl
                          5. installSSLHooks(libssl)
                          6. Hook SSL_CTX_use_certificate(X509*)
                          7. NativeFunction(i2d_X509) 序列化为 DER
                          8. ASN.1 扫序列号 → 写 cert_<SERIAL>.der
                          9. Hook SSL_*_PrivateKey_file → 打印临时私钥路径
                         10. openssl 转 PEM / 打 P12 → demo/
```

推荐调用（与 `readme.txt` 思路一致，参数以当前脚本为准）：

```bash
python realtime_process_monitor.py -e S2TD_Converter_v.2.2_CN_MT.exe -s dll_detection_hook.js
```

#### 技术要点 A：为何盯 `libssl-1_1.dll`

- 解包目录自带 OpenSSL 1.1：`libssl-1_1.dll` + `libcrypto-1_1.dll`
- Python / `cryptography` / `urllib3` 最终会走到这些 DLL 的 `SSL_CTX_use_certificate*` / `SSL_CTX_use_PrivateKey*`
- 监控器先用 `psutil.Process.memory_maps()` 判断进程是否已映射 `libssl-1_1`，再决定何时 `frida.attach`

#### 技术要点 B：证书从内存导出（不是读文件）

关键调用链在 `dll_detection_hook.js`：

1. Hook `SSL_CTX_use_certificate(SSL_CTX *ctx, X509 *x)`
2. 在 `onEnter` 拿到内存中的 `X509*`
3. 在 `libcrypto-1_1.dll` 上解析导出 `i2d_X509`
4. 调用：`derLength = i2d_X509(x509, &derPtr)`，再 `readByteArray(derLength)` 得到 DER
5. 简易 ASN.1 扫描 INTEGER(0x02) 提取序列号
6. 落盘：`cert_<SERIAL>.der`（对应 `demo/cert_52BFFC40F80002868FD599F03C66F84A98737EBB.der`）

要点：程序即使把证书只放在内存/临时区、不长期落盘，只要走 OpenSSL「设置客户端证书」API，就能被完整导出。

#### 技术要点 C：私钥如何拿到

Hook 对私钥走的是**路径泄露**，不是内存 dump：

- Hook `SSL_CTX_use_PrivateKey_file` / `SSL_use_PrivateKey_file`
- `onEnter` 读取 `args[1]` 的文件路径并打印
- 目标程序（Python）使用证书时，常把私钥写到类似 `tmpXXXX.pem` 的临时文件再交给 OpenSSL
- `demo/tmpvzd2agdz.pem` 即此类临时私钥文件的保留副本（与 `cert.pem` 配对，4096 位，已验证匹配）

脚本里虽枚举了 `SSL_CTX_use_PrivateKey` / `SSL_use_PrivateKey`（内存加载私钥），但**未对内存中的 EVP_PKEY 做 PEM/DER 导出**；本样本因走了 `*_file` 路径，路径泄露已足够。

#### 技术要点 D：事后格式转换（readme 记录）

```bash
# DER → PEM/CRT
openssl x509 -inform der -in cert_52BFFC40....der -out cert.crt

# 证 + 私钥 → P12，导入系统
openssl pkcs12 -export -in certificate.cer -inkey private.key -out output.p12 -name "My Certificate"

# 用证书直接请求
curl -v --cert cert.crt --key tmpvzd2agdz.pem https://lic.megacave.com/api/v2/get-csrf-token
```

#### 技术要点 E：附带能力

- `SSL_CTX_set_verify` / `SSL_set_verify`：把 verify mode 改成 `SSL_VERIFY_NONE`（便于本地抓包/中间人调试；对 Cloudflare 强制 mTLS 的远端仍必须带客户端证）
- `SSL_write` / `SSL_read`：在加解密后的缓冲区打印 HTTP 明文（可看到 `Cf-Client-Cert-Der-Base64` 等头与 body）

#### 抓取成果对照

| 产物 | 来源 |
|---|---|
| `demo/cert_52BFFC40....der` | Hook `SSL_CTX_use_certificate` + `i2d_X509` |
| `demo/cert.pem` / `Cf-Client-Cert.cer` | DER 转 PEM / 同证副本 |
| `demo/tmpvzd2agdz.pem` | Hook `SSL_*_PrivateKey_file` 泄露的临时路径后拷贝 |
| `demo/output.p12` | openssl 将 cer+key 导出为 PKCS#12（密码 `123456`） |
| `get.txt` 中 `Cf-Client-Cert-Der-Base64` | 可由 `SSL_write` 明文抓包或证书再编码得到 |

### 5.1b Body 解密密钥获取技术要点（v2.5_EN，无 Frida 注入）

#### 为何不用早期 Frida 注入

| 现象 | 原因 |
|---|---|
| `frida.spawn` / CreateProcess 挂起后注入 | 子进程从启动即加载 `frida-agent`，**GUI 经常不出现** |
| 对已运行子进程 `frida.attach` | 常报 `ProcessNotRespondingError`（抗注入） |
| Nuitka onefile | 父进程≈解压器（modules≈28–34），真应用在**有窗口的子进程** |

因此 v2.5 抓 body 密钥改用：**用户正常启动 → 选有窗口的子进程 → `ReadProcessMemory` 扫 PEM**。

#### 抓取流水线

```text
1. 双击启动 S2TD_Converter_v.2.5_EN.exe（管理员），确认 GUI 可见
2. python tmp/scan_process_pem.py -n S2TD_Converter_v.2.5_EN.exe
      - 枚举同名进程，优先 window=True 且 RSS 较大者（真子进程）
      - OpenProcess(PROCESS_VM_READ|QUERY)
      - VirtualQueryEx 遍历 MEM_COMMIT 可读区
      - 正则匹配 -----BEGIN ... -----END ...
3. 落盘 tmp/captured/pem_ext/
4. python tmp/try_scanned_keys.py
      - 校验 PEM；区分 2048 body 私钥 / 4096 mTLS 私钥 / 证书
      - 拷贝干净副本到 tmp/captured/keys_clean/
5. python tmp/verify_response_decrypt.py
      - 解 latest_body.json + 现场拉新响应再解，确认密钥正确
```

#### 技术要点 A：选对进程

- 同名两个进程：父（小 RSS、无窗口）/ 子（大 RSS、**有窗口**）
- 只扫有窗口的 PID，避免扫到 Nuitka 解压器

#### 技术要点 B：无注入读内存

- 不注入 DLL、不挂 Frida → 绕过「拒绝 frida-agent」
- 需管理员（目标 EXE `requireAdministrator`，同完整性级别才能 `OpenProcess`）
- PEM 在堆中以明文 ASCII 存在（cryptography / OpenSSL 加载后）

#### 技术要点 C：扫到的材料如何分类

| 特征 | 判定 |
|---|---|
| `BEGIN RSA PRIVATE KEY` / `PRIVATE KEY`，**2048 bit** | Body 客户端私钥 |
| `BEGIN PRIVATE KEY`，**4096 bit**，模数 = 客户端证公钥 | mTLS 私钥（与 §5.1 同源） |
| `BEGIN CERTIFICATE`，serial `52BFFC40...` | mTLS 客户端证 |
| 多把 `RSA PUBLIC KEY` 2048 | 含服务端/其它公钥候选 |
| `gAAAAA...` 片段 | Fernet token 残留（提示） |

垃圾命中（仅 BEGIN 头 + 二进制）：长度过短或无法 `load_pem_*` 的丢弃。

#### 技术要点 D：响应解密算法（已验证）

```python
# 解服务端响应
key_ct = b64decode(json["key"])          # 256 bytes
fernet_key = private_2048.decrypt(key_ct, padding.OAEP(
    mgf=padding.MGF1(hashes.SHA256()),
    algorithm=hashes.SHA256(),
    label=None,
))                                    # 44-byte urlsafe Fernet key
plaintext = Fernet(fernet_key).decrypt(b64decode(json["data"]))
```

验证结果（`tmp/verify_response_decrypt.py`，2026-08-01）：

| 样本 | 结果 |
|---|---|
| `tmp/latest_body.json` | OAEP-SHA256 + Fernet → `415 Unsupported Media Type...` |
| 现场新响应（mTLS GET） | OAEP-SHA256 + Fernet → `400 Bad Request...` |

→ **Body 2048 私钥正确**，可稳定解服务端响应。  
HTTP 4xx/5xx 明文是业务协议问题，与密钥无关。

### 5.1c 请求 Body 解密方法分析（`get.txt`）

#### 密码学方向（与响应相反）

| | 响应（已解开） | 请求（`get.txt`） |
|---|---|---|
| Fernet key 用谁的公钥加密 | 客户端 Body 公钥 | **服务端公钥** |
| 解密需要 | 客户端 2048 私钥 | **服务端 2048 私钥** |
| 本地是否持有 | 有（`body_rsa2048_private.pem`） | **无**（内存中只有服务端公钥） |

`tmp/analyze_request_body.py` 实测（2026-08-01）：

- Body 2048 / mTLS 4096 / demo 私钥：**全部无法** RSA 解密 `get.txt` 的 `key`
- Fernet 时间戳：`2025-09-08T00:49:56Z`（旧抓包，无法在现进程里找回当时 session key）
- 内存扫到的 2048 公钥中，**有对应私钥的只有客户端自己**；其余 9 把为「仅公钥」→ 服务端/外部候选
- 探测命中的服务端公钥：`keys_clean/server_pub.pem`（fp=`67e373694bf5a073`，OAEP，见 `server_pub_meta.json` / `license_client/probe_hit.json`）

#### 为何「解密旧请求」走不通

非对称加密的正常设计：客户端用服务端公钥封住 Fernet key，只有服务端能解。  
客户端进程里**不应**出现服务端私钥；本次扫描也未发现与 `server_pub` 模数匹配的私钥。

因此：**不能**像解响应那样用本地私钥解开 `get.txt`。

#### 可行替代路径（按推荐顺序）

1. **不必解密旧包 — 按同方案构造新请求**（已具备材料）  
   - 明文 → Fernet → `data`  
   - Fernet key → `server_pub` + **RSA-OAEP-SHA256** → `key`  
   - 实现：`tmp/body_crypto.py` 的 `seal()`；演示：`python tmp/demo_request_seal.py`  
   - 再用 mTLS 发出，响应用 `open_json(client_priv)` 解

2. **加密前截获明文 / Fernet key**（若必须看客户端真实业务字段） — **v2.2 已完成**  
   - v2.5 Frida 晚期注入常失败；可在触发联网授权时对有窗口进程做短时 `ReadProcessMemory`，搜 `gAAAAA` 与 44 字节 urlsafe Fernet key，用候选 key 试解刚发出的 `data`  
   - **v2.2（推荐）**：`python tmp/run_v22_http_capture.py` — spawn 后注入，monkeypatch `Fernet.encrypt` / `requests.Session.send`，启动自动联网即可写入 `tmp/captured/http_capture/requests_v22_*.jsonl`（见 §4.4、§5.1d）  
   - 历史上也曾尝试 Hook `RSA_public_encrypt` / `EVP_PKEY_encrypt`（主目录 `hook.js`）；Python 层 Fernet hook 对业务明文更直接

3. **获取服务端私钥**（通常不可行）  
   - 仅当服务端私钥误下发到客户端、或从服务端泄露时才可能直接解历史 `get.txt`

#### 请求 vs 响应代码对照

```python
# 请求（客户端 → 服务端）：seal
fkey = Fernet.generate_key()
data = b64(Fernet(fkey).encrypt(plaintext))
key  = b64(server_public.encrypt(fkey, OAEP_SHA256))

# 响应（服务端 → 客户端）：open —— 本地已验证
fkey = client_private.decrypt(b64(key), OAEP_SHA256)
plaintext = Fernet(fkey).decrypt(b64(data))
```

5. **成果**：见 §4.4（`token`/`product`；无版本号；三段 API 与响应明文）。

## 6. 攻击面与可行路线（分析视角）

按投入/收益排序：

### A. 密钥与协议状态（已闭环响应解密 + 请求明文）

1. Body 响应：**RSA-2048-OAEP-SHA256 + Fernet**，私钥见 `keys_clean/body_rsa2048_private.pem`（§5.1b）。  
2. `get.txt` 请求方向仍需**服务端公钥**加密；客户端私钥解不开请求 `key` 是正常现象；旧包不必解，用 `seal()` 即可重放形态。  
3. mTLS 与 Body 仍是两套密钥（4096 vs 2048）。  
4. 启动联网业务明文已掌握（§4.4）：`token` + `product`；版本号**不在**请求报文中。

### B. 客户端证书实测（`simple_client_test.py`，2026-08-01）

实跑结果要点：

| 观察 | 含义 |
|---|---|
| 请求“成功”返回 JSON | **mTLS 已通过**（证书+私钥有效） |
| HTTP **500** | 应用层失败：裸 GET、未带加密业务 body / 完整协议头 |
| `Set-Cookie: session=...` | Flask/itsdangerous；payload 明文含 `csrf_token=da6bf184...` |
| Body `{"data","key"}` | 与 `get.txt` 同构：Fernet + RSA-2048 密文（256B） |
| `rsa_test` 私钥解不开本次 `key` | 服务端包装响应用的 **不是** demo 这把 2048 密钥；也不是 mTLS 4096 证 |

结论：`simple_client_test.py` 只证明传输层；Body 密钥见 §5.1b，响应解密见 `verify_response_decrypt.py`。

### C. Body 密钥与响应解密（详见 §5.1b）

技术路径与产物见 **§5.1b**。一句话：无注入内存扫 PEM → `keys_clean/` → OAEP-SHA256 解响应，已通过保存样例与现场样例双验证。

### D. 客户端证书滥用

已持有 mTLS 材料 → 可伪造“正版客户端”身份调 `lic.megacave.com`。  
仍受 Body 加密与服务端业务校验限制；单独证书不足以绕过授权逻辑。

### E. PyArmor 脱壳

- 当前 **1shot 不适配**  
- 可选：旧版 `_pytransform` 专用工具、调试器 dump co_code、PyArmor 运行时 hook `__pyarmor__`  
- 脱壳后目标：授权校验、RSA 公钥/私钥、API 列表、机器码算法（`get_machine_id_CLAUDE`）

### F. 本地 License 绕过

脱壳或内存补丁跳过联网校验 / 永久成功分支。依赖找到校验点（PyQt 回调或 helpers 内）。未脱壳前成本高。

### G. 协议重放

Fernet 含时间戳；服务端若校验 TTL/nonce，裸重放 `get.txt` 多半失败。需能现场加密新 body。

## 附录 B — 响应解密伪代码（已验证）

```python
from cryptography.hazmat.primitives.asymmetric import padding
from cryptography.hazmat.primitives import hashes, serialization
from cryptography.fernet import Fernet
import base64, json

priv = serialization.load_pem_private_key(
    open("tmp/captured/keys_clean/body_rsa2048_private.pem", "rb").read(),
    password=None,
)
obj = json.load(open("tmp/latest_body.json", encoding="utf-8"))
key_ct = base64.urlsafe_b64decode(obj["key"] + "=" * ((4 - len(obj["key"]) % 4) % 4))
data = base64.urlsafe_b64decode(obj["data"] + "=" * ((4 - len(obj["data"]) % 4) % 4))
fernet_key = priv.decrypt(
    key_ct,
    padding.OAEP(mgf=padding.MGF1(hashes.SHA256()), algorithm=hashes.SHA256(), label=None),
)
plaintext = Fernet(fernet_key).decrypt(data)
print(plaintext)
```
